    Hardware sizing: what a Minder box needs, by camera count, with and without the language model¶

    This guide sizes a box for Minder in its two modes:

    • Without the language model (MINDER_LLM=off): detection, alerts, faces, history, search, Home Assistant and the portal. Nothing calls a language model.
    • With the language model (MINDER_LLM=on): the same, plus chat understanding, alert descriptions and confirmation of escalated rules by gemma3:4b through Ollama.

    Each camera count has a minimum (it runs, with little headroom) and a comfortable option (peaks such as rain, foliage or a busy evening don't drop frames). Every figure is marked measured or estimated. Measured figures come from the reference box (below). Estimated ones are extrapolated from those measurements and should be confirmed on your own hardware with the checks at the end.

    The reference box (where "measured" comes from)¶

    Part Value
    CPU Intel Core i7-8750H: 6 cores / 12 threads, 8 threads given to WSL2
    Memory 35 GB visible to WSL2
    GPU NVIDIA GTX 1050 Ti, 4 GB (Pascal, compute capability 6.1), CUDA through WSL2's /dev/dxg
    Cameras 8 streaming: 7 detect on a 352×288 substream, 1 on 1280×720, all at 5 fps; recording on detections and alerts, kept 2 days
    Detector Frigate 0.17, yolov8n at 320×320. ONNX on the CUDA execution provider (GPU), or OpenVINO on the CPU

    Measured on 2026-10-09:

    What Measured
    Detector time per inference, GPU (yolov8n-320, CUDA) 9.6–12.7 ms live, about 95 inferences/s of capacity
    Detector time per inference, CPU (yolov8n-320, OpenVINO) 32.5 ms live, about 30 inferences/s of capacity
    Detector load from 8 cameras 25 inferences/s quiet; 38–56/s in rain with foliage moving; up to 6/s from one busy camera
    CPU detector at 8 cameras at capacity but working: 31.7/s asked of 30.8/s, ~0.1 frames/s skipped in rain, host CPU ~70% busy. This is how the box ran for weeks with the language model on
    GPU detector at 8 cameras 0 frames skipped, host CPU ~30% busy, Frigate ~1.9 threads in total
    Decode + motion + tracking per camera about 0.10–0.12 of one CPU thread (substream or 720p)
    Memory, per container Frigate 2.5 GB · Minder 1.5 GB · Home Assistant 0.35 GB · Mosquitto < 0.01 GB
    GPU memory, detector 731 MiB (out of 4 GB)
    GPU memory, gemma3:4b 2.9 GB resident at 4096 context (Ollama), up to ~3.7 GB measured earlier with vision
    Host RAM, Ollama's llama-server with gemma3:4b loaded 8.4 GB RSS, of which the model file mapped into memory is a large share
    Router (chat understanding) on the GPU 1.22 s median
    gemma3:4b on the CPU, isolated (8 threads) 7.1 tokens/s. With Frigate running it fell to 0.3 tokens/s
    Recording, detections + alerts, 2 days, 8 cameras 0.9 GB

    The detector is what sets the camera count. Decoding is cheap at substream resolution, but each camera adds about 3–6 detector inferences per second when there is motion. The CPU detector handles about 30/s on this CPU: 4–5 cameras comfortably, and 8 at capacity (measured). The GPU detector handles about 95/s.

    Without the language model (MINDER_LLM=off)¶

    CPU by camera count¶

    Cameras Detector Minimum CPU Comfortable CPU Basis
    1–2 CPU (OpenVINO) 4 cores / 4 threads, x86-64 with AVX2 (Intel 8th gen / AMD Zen or newer) 4 cores / 8 threads estimated: ≤12 inferences/s at peak, under half the measured CPU detector capacity
    3–4 CPU (OpenVINO) 4 cores / 8 threads 6 cores / 12 threads estimated: ≤24/s at peak, about 80% of the measured capacity
    5–6 CPU, or GPU 6 cores / 12 threads, no GPU 4 cores / 8 threads plus a GPU, or 8 cores / 16 threads without one estimated: 30–36/s at peak is at the CPU detector's capacity
    7–8 CPU, or GPU 6 cores / 12 threads (8 threads in use), no GPU: works, with an occasional skipped frame at peaks · or 4 cores / 8 threads + GPU 6 cores / 12 threads + GPU measured both ways: the CPU detector runs at capacity (~0.1 skipped frames/s in rain, host 70% busy); the GPU leaves the host 70% idle with 0 skipped
    9–12 GPU 4 cores / 8 threads + GPU 6 cores / 12 threads + GPU estimated: ≤72/s at peak against the measured ~95/s GPU capacity; about 1.5 threads for decoding
    13–16 GPU 6 cores / 12 threads + GPU 8 cores / 16 threads + GPU estimated: ~96/s at peak is at the 1050 Ti's limit; use a faster GPU for headroom
    17+ GPU, faster than a 1050 Ti not measured not measured size from the checks at the end

    Rules of thumb behind the table (estimated from the measurements):

    • Host CPU with a GPU detector: about 1.5 threads for Minder, Home Assistant and Frigate's fixed processes, plus about 0.12 of a thread per camera. Add headroom for Minder's second look (YOLO 640 on the CPU, run once per alert) and for semantic search indexing after each event.
    • CPU detector: each inference per second costs about 0.1 of a thread on this CPU. Budget 6 inferences/s per camera for peaks, and keep the total under about 80% of the detector's capacity.
    • Detecting on a full-resolution stream costs about the same decoding per camera as a substream (measured: 0.12 thread at 720p). Each inference then covers a smaller share of the frame, so expect more inferences in busy scenes. This is the remedy for distant subjects that the 352×288 substream misses, and a GPU leaves room for it.

    GPU by camera count¶

    Cameras Minimum GPU Comfortable GPU
    1–4 none: the CPU detector is enough none, or any CUDA GPU to free the CPU
    5–8 none: the CPU detector copes at capacity (measured at 8) NVIDIA, CUDA, compute capability ≥ 6.0 (Pascal or newer), 2–4 GB. Measured on a 4 GB GTX 1050 Ti: 731 MiB used, 9–28% busy
    9–16 4 GB, GTX 1050 Ti class 4 GB or more, GTX 1650 / RTX 3050 class or newer, for headroom over the 1050 Ti's ~95/s

    The detector uses about 0.7 GB of GPU memory, so memory isn't the limit; inference speed is. A larger model (yolov8n at 640: 20.7 ms, or yolov8s at 640: 29.6 ms, both measured on the 1050 Ti) improves distant detection and lowers capacity to about 48/s or 34/s. Choose it per box with the checks below.

    Memory by camera count¶

    Cameras Minimum RAM Comfortable RAM Basis
    1–4 8 GB 16 GB estimated: ~3.5 GB of containers plus the OS
    5–8 12 GB 16 GB measured: 4.4 GB of containers at 8 cameras, plus the OS and page cache for recordings
    9–16 16 GB 24–32 GB estimated: Frigate grows by about 0.2 GB per camera

    Disk: recordings of detections and alerts only, kept 2 days, measured 0.9 GB for 8 cameras. Continuous recording is far larger. Estimate it from your cameras' bitrates: a 2 Mbit/s stream is about 21 GB per camera per day. Use a separate disk for /media/frigate, not the system SSD.

    With the language model (MINDER_LLM=on)¶

    The model, gemma3:4b, wants a GPU with at least 4 GB to itself. On the CPU it works, but slowly: 7.1 tokens/s measured with nothing else running, a description in ~30 s instead of ~7 s, and a routed answer in 5–8 s (see Using Minder). Next to a busy CPU detector it slows down much further: one WSL2 run measured 0.3 tokens/s. A CPU-only box with the model on is therefore for 4 cameras or fewer, with 16 GB RAM and 6 cores / 12 threads or more.

    On a 4 GB card the model and the detector load together, but they don't run well together. Measured on the reference box with both on the GTX 1050 Ti:

    Model alone on the GPU Model + detector on one 4 GB card
    GPU memory 2.9–3.7 GB 3993 of 4096 MiB: full
    Model speed ~20 tokens/s 4.8 tokens/s warm, 1.6 tokens/s when the idle model had been paged out to system RAM
    Detector while the model answers 10 ms, 0 skipped 10–72 ms, 18–21 frames/s skipped across all cameras for the 15–17 s of each answer

    With the card full, the driver keeps moving memory between the card and system RAM (seen here on WSL2). The model slows to a quarter of its speed, and Frigate stops seeing for as long as each answer takes. So the platform profile's detector_when_llm therefore moves Frigate's detector back to the CPU while the model is on, and the camera count falls back to the CPU detector's limits: 8 cameras on a 6-core CPU is the measured ceiling, at capacity.

    Cameras Minimum Comfortable Basis
    1–2 4 cores / 8 threads · NVIDIA 4 GB for the model · 16 GB RAM 6 cores / 12 threads · 4 GB GPU · 16 GB RAM estimated from the CPU detector + measured model footprint
    3–4 6 cores / 12 threads · 4 GB GPU · 16 GB RAM 6–8 cores · 4 GB GPU · 24 GB RAM estimated: the CPU detector at ~80% of its capacity in peaks
    5–8 6 cores / 12 threads · 4 GB GPU for the model, detector on the CPU · 16 GB RAM 8 cores / 16 threads · 6 GB GPU at least, 8 GB better, model and detector both on it · 32 GB RAM measured minimum: the reference box ran 8 cameras like this, with the CPU detector at capacity (~0.1 skipped frames/s in rain, host 70% busy, little room for anything else). Comfortable is estimated: 3.7 GB model + 0.7 GB detector needs more than 4 GB (measured above); 6 GB leaves ~1.5 GB spare
    9–16 8 cores / 16 threads · 6–8 GB GPU · 24 GB RAM 8+ cores · 12 GB GPU or more · 32 GB RAM estimated: 3.7 GB model + 0.7 GB detector + headroom

    Notes for the language model mode:

    • RAM: add 4 GB minimum, 8 GB comfortable, to the no-model figures for Ollama. Its llama-server measured 8.4 GB RSS, which includes the mapped model file. The OS can reclaim that part under pressure, but loading becomes slow if it does.
    • A GPU with 6 GB or more (8 GB for headroom) can hold the model (~3.7 GB) and the detector (~0.7 GB) together. Remove detector_when_llm from /data/platform.yaml so the detector stays on the GPU in both modes. This combination is not yet measured. scripts/platform_detect.py --write --force writes the key back, so redo the edit after re-detecting.
    • Response time: chat understanding measured 1.22 s median on the 1050 Ti. A newer GPU is faster. Alert descriptions take a few seconds and arrive after the photo.

    Devices¶

    Home Assistant devices (lights, plugs, locks, sensors) cost next to nothing to run. Home Assistant measured 0.35 GB here, and Minder reads devices only when asked or when a rule runs. Dozens to low hundreds of devices don't change any figure above. Cameras and the detector set the size of the box; devices don't.

    ARM boards¶

    Nothing here was measured on ARM. A Jetson Orin Nano 8 GB is the candidate for the no-model mode (the model alone would take ~3.7 GB of its 8 GB shared memory). Check it with the steps below before relying on it.

    Checking your own box¶

    1. Detector capacity: in Frigate's System page, or with docker exec minder-frigate-1 curl -s localhost:5000/api/stats, read the detector's inference_speed in ms. Capacity is 1000 ÷ that, in inferences/s.
    2. Detector load: add up detection_fps across cameras at a busy time (rain, wind, evening). Keep it under 80% of capacity. If any camera shows skipped_fps above 0, the detector is short.
    3. Host CPU and memory: docker stats --no-stream. The minder-frigate-1 row is decoding plus the detector's host side.
    4. GPU: nvidia-smi for memory and use, and ollama ps to see whether the model is resident and on the GPU (100% GPU).
    5. Health: the portal's health page shows which detector Frigate runs and why, for example "on the GPU (MINDER_LLM=off)" or "on the CPU while the language model holds the GPU".
