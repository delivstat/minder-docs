    Moving the language model to the cloud¶

    Minder's language model can run on a cloud provider instead of on the appliance. The box then needs no graphics card and no Ollama. Detection, alerts, recordings, faces and search stay on the box exactly as before. What moves is the part that reads language: chat, rules written as a sentence, history questions, and descriptions of what a camera sees.

    This guide moves an existing installation from the local model (Ollama) to OpenRouter, the cloud provider built into Minder's runtime. It takes about ten minutes, and it can be reversed by putting four lines back.

    Before you start: turn alert descriptions off¶

    We recommend MINDER_DESCRIBE=off on any box whose model is in the cloud. The description written for each alert (the sentence "a person in a red jacket at the gate, carrying a parcel") is the model call Minder makes most often, by far:

    • Volume. It runs once per alert, so it follows how busy your cameras are, not how much anyone uses Minder. On the reference installation, eight cameras produce about 80 person alerts a day: around 2,400 descriptions a month. Chat, by comparison, is a handful of messages a day.
    • Every description sends a picture. Each one uploads the alert's camera frame to the provider. With descriptions off, a frame leaves the house only when someone asks a question about a camera.
    • Nothing important is lost. The alert still arrives at once, with the photo, every detected object boxed, and the clip. Only the follow-up sentence is dropped.

    With descriptions off, the monthly bill follows what people ask, which is what a subscription should pay for.

    What you need¶

    • An OpenRouter account and API key (openrouter.ai), with credit or a plan.
    • Two model names from OpenRouter's catalogue:
    • a router model, which reads each message into a structured plan. It must support structured outputs (JSON schema); OpenRouter's model page lists the parameters each model supports.
    • a vision model that accepts images, for scene questions, general chat and (if you keep them) descriptions. google/gemini-2.5-flash is the model Minder already uses for its optional cloud features, and it describes scenes well.

    Choose the router model with care. How well it reads requests decides how well Minder understands you. The local default, gemma3:4b, reads 94.6% of Minder's 194 recorded test messages correctly, and a cloud model should be measured on the same messages before you rely on it (see Checking the router model).

    Step 1: edit .env¶

    In the Minder directory (~/minder), set these lines in .env. Add any that are missing:

    MINDER_LLM=on
OPENROUTER_API_KEY=sk-or-...

# The router: reads each message into a plan.
MINDER_ROUTER_PROVIDER=openrouter
MINDER_ROUTER_MODEL=<router model id>

# The vision profile: chat, scene questions, descriptions, and the local tier of a rule's check.
MINDER_VISION_PROVIDER=openrouter
MINDER_VISION_MODEL=<vision model id, e.g. google/gemini-2.5-flash>

# Recommended: no description per alert (see above).
MINDER_DESCRIBE=off

    Leave MINDER_QUERY_PROVIDER as it is. With the vision profile in the cloud, scene questions go to the cloud either way.

    If your .env still has MINDER_DESCRIBE_PROVIDER or MINDER_QUERY_MODEL, delete them. They chose nothing (descriptions follow MINDER_VISION_PROVIDER), and current versions ignore them.

    Step 2: restart¶

    ./minder up

    It rebuilds if needed, restarts Minder and waits until it answers.

    Step 3: check the health page¶

    Open the portal's Settings tab and find Health & Recovery. Three rows tell you the move worked. A row that is ok shows its detail when you hover over the state:

    Row State Detail
    Ollama (LLM/VLM) ok not used (no model profile names ollama)
    Alert descriptions off off (MINDER_DESCRIBE=off): alerts carry the photo and clip
    Frigate detector ok on a box with an NVIDIA card: on the GPU (the language model runs on a cloud provider)

    The last one is a bonus. Nothing on the box needs the graphics card for the model any more, so Frigate's detector gets it: faster detection, and no skipped frames in rain or wind.

    Step 4: try it¶

    In the portal's Chat tab, or on Telegram or Discord:

    • "is anyone at the front door?" (a live check, answered from the camera);
    • "who came by today?" (history);
    • "what's happening on the porch?" (a scene question: this one sends the frame to the cloud);
    • "alert me when someone is at the gate after 10pm" (a rule from a sentence).

    Each should answer as it did with the local model. If a message gets a wrong kind of answer (a history list when you asked for a live check, say), the router model is misreading it; see below.

    Step 5 (optional): retire Ollama¶

    Minder no longer calls Ollama. To free its memory and the graphics card for good, stop it on the host:

    sudo systemctl disable --now ollama

    The downloaded models stay on disk (usually /usr/share/ollama/.ollama/models) in case you move back.

    What leaves the house¶

    With the model in the cloud, these go to OpenRouter and the model provider behind it:

    • the text of every chat message, with the names of your cameras and devices (the router needs them to understand "turn off the pump");
    • a camera snapshot when someone asks about a scene;
    • a snapshot for each alert, only if you leave descriptions on;
    • a snapshot for the second look on a rule you gave a severity check.

    Recordings, the event history, face templates and the search index never leave the box. Alerts reach you through Telegram or Discord as before. Read Privacy for the full picture.

    When the internet is down¶

    Detection and alerts don't use the model, so they keep working, with photos and clips. When the router can't be reached, chat falls back to the keyword reader Minder uses when the model is off, so live checks, history, "show me" and device commands still get answers. Anything that needs the model itself (open questions about a scene, rules from a free-form sentence, descriptions) waits until the connection is back.

    What it costs¶

    Count the calls, then look up your models' prices on OpenRouter:

    Call How often Sends
    Router once per chat message up to about 800 tokens of text: the message, your camera and device names, the instructions
    Scene question or open chat when someone asks one a camera frame and a short prompt
    Alert description once per alert, if on a camera frame and a short prompt

    To see how many alerts your cameras produce, look at a typical day in the portal's Events tab. That number, times 30, is what descriptions would add each month.

    Checking the router model¶

    Minder ships a benchmark of 194 recorded messages with the intent each one should get. It runs them through the real router on your box and reports how many were read correctly, before and after its built-in guards, with timing:

    scripts/bench_isolated.sh topology

    It stops the appliance while it runs (a timer restarts it within 45 minutes even if the run dies) and records the result under baseline/. With the router on OpenRouter, it measures the cloud model and costs the price of 194 short requests. Compare its two percentages with gemma3:4b's: 86.4% raw and 94.6% with guards.

    Moving back¶

    Set the two providers back to ollama and the two models back to local ones, start Ollama again, and run ./minder up:

    MINDER_ROUTER_PROVIDER=ollama
MINDER_ROUTER_MODEL=gemma3:4b
MINDER_VISION_PROVIDER=ollama
MINDER_VISION_MODEL=gemma3:4b

    MINDER_DESCRIBE can stay off or go back on; with a local model the descriptions cost nothing but graphics-card time.
