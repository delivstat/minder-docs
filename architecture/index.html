    How Minder works¶

    The technical picture: what runs, what talks to what, and why it is arranged this way. For using Minder, see Using Minder. For the reasoning behind individual decisions, the design/ directory has 21 notes — this page is the map that tells you which one to open.

    The shape¶

    Five containers on one host, all on the host network:

    Container What it does
    frigate Camera detection — RTSP in, object detections out over MQTT
    mosquitto The MQTT bus everything else talks over
    homeassistant Device control (lights, switches, sensors) — a hidden integration layer
    minder Everything that is Minder: the swarm, the bots, the webapp
    frigate-init One-shot: writes Frigate's config from your camera list, then exits

    Ollama is a host prerequisite, not a container. The router and vision models run on the host and are reached over localhost:11434 (the stack is on the host network). That is deliberate — it is what keeps camera frames inside the house — but it does mean docker compose up alone is not enough on a fresh machine: qwen2.5:3b and qwen2.5vl:3b must be pulled first.

    The minder container supervises four processes:

    swarmkit serve /app/workspace --port 8321   # the agent swarm, HTTP on localhost
python3 /app/webapp/app.py                  # onboarding + ops API, port 80
python3 /app/bot.py                         # Telegram adapter
python3 /app/discord_bot.py                 # Discord adapter

    Each is restarted independently if it dies. A crashed Telegram bot does not take the cameras with it.

    The core idea: the model reads, the code does¶

    This is the decision everything else follows from (design/conversation-router.md).

    When you send a message, a small local model does exactly one job: turn your sentence into a structured plan — which kind of request is this, which camera, which device, what condition. It does not act. It does not call tools in a loop. It emits a plan and stops.

    Deterministic Python then executes that plan.

    "is someone at the main door"
   → router: {kind: query, camera: Front-Door}
   → code: fetch snapshot → describe → reply

    The reason is reliability. An agent that decides and acts in a loop fails in ways you cannot reproduce: it retries, it hallucinates a camera name, it takes a different path on identical input. Splitting them means the only thing that varies is the parse — and the parse is testable. scripts/router_cases.json pins 166 utterances against expected intents, drawn from this appliance's own camera and device names.

    The guards¶

    A 3B does not parse well enough on its own. Measured on those 166 cases, qwen2.5:3b gets the intent right 62% of the time — not usable for a system that switches your pump.

    So the plan passes through a deterministic correction pass (_correct_plan) before anything acts on it. That takes the same model to 90%, and no guard has ever cost a case that was previously right:

    intent correct
    the model alone 62.2%
    after the guards 90.4%

    The guards are not patches around a bad model — they are what makes a local 3B viable, and so they are the reason Minder needs no cloud for language. Each one restates something an intent already means:

    • A scenario is a standing rule with a future trigger — so "turn on the pump", with no trigger, is a command, not a rule. This one matters beyond accuracy: a scenario is stored, so a misread command silently never runs.
    • A device command must say what to do — so "what smart plugs do I have" is a question, not an instruction to switch one.
    • A message naming a camera is about that camera — the names are Side-Gate, people type "bedroom deck", and matching those is code's job rather than the model's.

    They are also specific to the model deployed. Benchmarked against a larger qwen3.5:4b, the same guards helped nothing — that model does not make these mistakes. Change the router model and the guards should be re-measured rather than trusted.

    Measuring it yourself¶

    docker compose exec minder python /app/scripts/bench_router.py /app/scripts/router_cases.json

    Prints per-intent accuracy, what the guards changed, and latency. It asks the model once per case and scores the answer twice — before and after the guards — so the difference between the two numbers is the guards and not sampling noise.

    Every routing decision is also recorded to the observation log (router_log.py), with the utterance, the model's intent and the guards' intent. scripts/harvest_router_cases.py turns that traffic into new labelled cases, so the benchmark grows toward what your household actually says rather than what we imagined it would. MINDER_ROUTER_LOG=off disables the recording.

    The swarm¶

    The workspace holds nine topologies, each a bounded job:

    Topology Job
    minder-router Parse a message into a plan (the hot path)
    minder-core The general conversational agent
    minder-device Device control through Home Assistant
    minder-discover Find cameras on the network
    minder-doctor Self-diagnosis — the six-hourly health check
    minder-frigate-config Write Frigate's configuration
    minder-ha-setup Home Assistant onboarding
    minder-onboard First-run setup
    minder-weather Weather lookups

    They run on SwarmKit, pinned once as SWARMKIT_VERSION in docker-compose.yml. Minder consumes the released runtime from PyPI — there is no path into a SwarmKit checkout anywhere in this repo.

    Tools reach the swarm as six MCP servers (mcp-servers/): camera, vision, detect, tuya, doctor, frigate. Each is a stdio subprocess the runtime governs — every tool call is policy-checked and audited.

    Vision: two layers, local first¶

    design/two-layer-vision-models.md has the full argument.

    • Layer 1 — per-alert enrichment. Runs on every alert, so it must be cheap: a small local VLM (Ollama, CPU) that says what is in frame.
    • Layer 2 — interactive questions. "What is the person doing?", "is that dangerous?" — a capable model that reads and judges. Local by default, cloud when you enable it.

    Vision runs on CPU deliberately. On this hardware the GPU thrashes between the detector and the VLM, and the CPU path is slower per call but does not destabilise detection (design/vision-architecture.md).

    Cloud escalation is opt-in per layer (MINDER_DESCRIBE_PROVIDER, MINDER_QUERY_PROVIDER) and falls back to local on failure — a cloud outage degrades quality, never availability.

    Detection plugins¶

    Optional perception — faces today, cartons on a belt or hard-hats tomorrow — added without a rebuild and without touching the detection path (design/detection-plugins.md).

    A plugin is a directory in /data/plugins/ holding a manifest, some code, and a model fetched on install with a checksum. Models are not baked into the image: it is already ~3GB, and one nobody arms is a pure tax.

    Three levels of "off", and they differ¶

    State Meaning Costs
    not installed no manifest, no model nothing
    installed registered, authorable in rules, model not loaded disk
    armed model resident, running on a cadence CPU

    The middle one is the point: you can install something to look at it without paying for it. Nothing loads until you arm it, and MINDER_PLUGINS=off stops all of it regardless.

    Declared cost is what makes arming safe¶

    Every manifest states what it costs, so Minder can refuse the third heavy plugin with a reason you can act on rather than you discovering it later as Frigate dropping frames:

    Face needs 7.5% of a core (750ms every 10s); already armed: Carton counter 3.6%;
budget is 25%. Disarm something or raise MINDER_PLUGIN_CPU_BUDGET.

    The budget is continuous cost — 180ms every 5s is 3.6% of a core — because that is what runs out, not peak inference time.

    Plugins are classified by what they remember¶

    Not by what they detect. Governance follows the kind automatically, so a plugin author cannot skip the consent machinery by not thinking about it.

    Kind Keeps Examples Brings with it
    detector nothing between frames faces-without-names, cartons, PPE nothing
    identifier templates identifying a person face recognition, ANPR enrolment, consent, retention, provable deletion
    tracker cross-frame state, no identity loitering, queue length a memory bound

    A licence plate identifies a person as surely as a face does — ANPR is an identifier.

    What a plugin may not do¶

    • It cannot set alert severity. What a plugin returns has no field for it, so a badly-tuned detector cannot wake you at 3am.
    • It cannot suppress an alert. The runner has no route to the alert path at all — a test asserts that on its source. A plugin annotates; Minder's rules decide.

    A wrong match therefore costs a wrong name rather than a missed event, and the security behaviour does not depend on any plugin being accurate.

    Frames: they get what they asked for¶

    Frigate detects on the 352x288 substream — enough to find a person, not to identify one. A plugin that needs resolution declares frame.source: main, and gets one on-demand grab when a detection says there is something worth looking at. Never a second continuous decode: an N100 cannot decode eight main streams, but it can afford one frame on a rare event.

    Minder then crops to the box Frigate already found. Measured here: 185x398 out of 2560x1440 — 2% of the pixels at full resolution, and YuNet runs in 9ms instead of 453ms. Cheaper than scanning the frame and sharper than shrinking it.

    A plugin that asked for the main stream is never handed a substream frame instead — it would answer confidently on it. A camera whose main stream is unreachable simply cannot serve that plugin, and the plugin list says which cameras it can.

    The grab is deleted as soon as the plugins have looked: it is a full-resolution photograph of whoever was at the door, and Frigate's own snapshot is the retained record.

    Installing¶

    docker compose exec minder python -c "
import plugin_install as pi; print(pi.install('face-detect'))"

    Installing never arms. Reinstalling to repair a corrupt model never changes what is armed.

    Events and alerts¶

    camera → frigate → MQTT (frigate/events) → minder
   → is this camera armed? is it in quiet hours? does a rule match?
   → describe the frame
   → alert bus (MQTT minder/alerts)
   → telegram / discord adapters

    The alert bus is the seam that makes channels pluggable (design/messaging-adapters.md). Minder publishes an alert once; each adapter subscribes and renders it its own way. Adding a channel means adding a subscriber, not touching the detection path. It exists because India blocked Telegram and the product needed a second channel without a rewrite.

    Scenario Studio¶

    Rules you describe in words — "turn on the pump when there is a person at the main door" — become running automations. Five design notes cover it (design/scenario-studio*.md): count thresholds, zones, cross-camera conditions, quick mode, severity escalation.

    The important property: a rule is data, not generated code. You can list, inspect and delete rules, and Minder shows you the rule it wrote before it starts running it.

    State¶

    Where What
    minder_minder-data volume → /data cameras, events, rules, channel config, monitor state
    minder_ha-config volume Home Assistant's own configuration
    minder_frigate-media volume recordings and snapshots
    backups/ (bind mount) nightly backups, kept on the host
    workspace/.swarmkit/ audit log, conversations, run state

    The compose project name is pinned to minder in docker-compose.yml. Volume names are prefixed with the project name, which compose otherwise infers from the directory — so an unpinned project in a renamed directory silently creates new, empty volumes while the real ones sit untouched on disk. That is a wiped-appliance-shaped failure with a one-line cause; the pin removes it.

    Operating it¶

    cd ~/minder
docker compose up -d              # start
docker compose logs -f minder     # watch
docker compose restart minder     # restart just the swarm container
    • Minder's SwarmKit server is on 8321, the webapp on 80. Because everything is network_mode: host, anything else on this machine must avoid those ports.
    • Telemetry is off by default. MINDER_OTEL=otlp enables OTLP export to a collector on localhost:4318. It used to default on, and with no collector listening it logged a connection error every ~20 seconds until the real logs were unreadable.
    • The nightly backup writes to backups/. Restore from the web UI.

    Tests¶

    docker build -t minder-ci . && docker run --rm -v "$PWD:/app" -w /app --entrypoint sh minder-ci -c \
  'uv pip install --system -q pytest && python -m pytest -q'

    Tests run inside the image because several reference /app paths that only exist in the container. 139 tests; 7 currently fail. Those seven are pre-existing — this suite lived in a repo whose pytest configuration excluded it, so it had never run as a suite until the extraction. CI deselects them by name and re-runs them in a second informational job, so the count is visible and goes down. See the README.
