    How Minder works¶

    The technical design of Minder as it runs today: every core subsystem and every feature, each as a decision and the reason for it. For using Minder, see Using Minder. For the argument behind any one decision at full length — including the options that lost — the design/ directory has 24 notes, and design/README.md is the audited index of what each one decided and whether it shipped.

    The reasons are written down because on an appliance they are load-bearing. Several decisions here were reversed after a measurement contradicted what looked obviously true; each reversal is noted where it happened and collected at the end. Where a number is quoted it was measured on the reference machine — an i7-8750H with a 4 GB GTX 1050 Ti and seven cameras — with a script that is in the repository and can be re-run.

    1. What Minder is¶

    A home security appliance that watches cameras, tells you in plain words what it saw, and does what you ask it in plain words — running entirely on one small computer in the house. No frame leaves the building unless you turn a cloud tier on.

    Four properties follow from "appliance", and most decisions below trace back to one of them:

    1. It must keep working when everything else fails — the language model down, the network down, an accelerator driver missing, a channel blocked. Detection is the floor; everything else degrades above it and says so.
    2. It runs on a 4 GB card and a laptop-class CPU. Every model choice is a residency question before it is a quality question.
    3. Nobody is watching the logs. A silent failure is worse than a loud one; a component that is quietly not doing its job must show on the dashboard in words.
    4. It is talked to, not configured. A household says "alert me if someone is at the gate after dark"; that sentence must become a running rule, and the household must be able to read the rule back.

    2. The shape¶

    Five containers on one host, all on the host network, plus one host process:

    Container What it does
    frigate Camera detection — RTSP in, tracked objects out over MQTT, recordings and snapshots
    mosquitto The MQTT bus: Frigate's events in, Minder's alerts out
    homeassistant Device control (switches, lights, sensors) and weather — a hidden integration layer
    minder Everything that is Minder: the swarm, the ops API and dashboard, the channel adapters
    frigate-init One-shot: writes Frigate's configuration from the camera list, then exits

    Ollama is a host process, not a container. The models are reached over localhost:11434. That keeps camera frames on the host and lets the GPU be shared by exactly one thing; it also means a fresh machine needs two models pulled before the stack is useful — gemma3:4b (routing and vision, one resident model) and qwen2.5:3b (the tool-using agents). MODELS.md lists every model, which property sets it and the benchmark behind each choice, and is generated from the repository because an inventory assembled by hand from five places is the document most certain to rot.

    The minder container supervises four processes, each restarted independently five seconds after a crash — a dead Telegram bot does not take the cameras with it:

    swarmkit serve /app/workspace --port 8321   # the agent swarm, HTTP on localhost only
python3 /app/webapp/app.py                  # onboarding, dashboard, ops API — port 80
python3 /app/bot.py                         # Telegram adapter
python3 /app/discord_bot.py                 # Discord adapter

    The swarm runs on SwarmKit, pinned once as SWARMKIT_VERSION in docker-compose.yml, consumed from PyPI. Tools reach it as four MCP servers (camera, tuya — Home Assistant —, doctor, frigate), each a stdio subprocess the runtime governs: every tool call is policy-checked and audited.

    3. The principles¶

    Five rules recur in every subsystem. They are stated once here so the sections can refer to them.

    The model reads, the code does. A language model turns a sentence into a structured plan and stops; deterministic Python executes the plan. Never an agent that decides and acts in a loop — that fails in ways you cannot reproduce. The only thing that varies is the parse, and the parse is testable.

    Everything is data. Rules, zones, plugins, backends, models, the platform — YAML or JSON files you can read, list and delete. No feature generates code.

    Local first; cloud is a tier you turn on. Every path has a fully local form. A cloud tier improves quality and, when it fails, falls back to local: a cloud outage degrades quality, never availability.

    Fail open on infrastructure, closed on evidence. When Minder cannot look (no frame, a model down), the safe behaviour is the old behaviour. When it looked and saw nothing, the safe behaviour is to say nothing — and record that it did.

    Measure, then decide; and say so when it reverses. Every model, prompt and residency choice in this document has a script behind it. The ones that were reversed are listed in §14 with the number that reversed them.

    4. Conversation: from a sentence to an action¶

    design/conversation-router.md, design/alert-quality.md §part 3.

    Every message from every channel arrives at one function, handle_message, and goes through four stages:

    "is someone at the main door"
   1. feedback?      no
   2. pre-route      no pattern matches → the model decides
   3. router         gemma3:4b → {kind: query, subject: person, cameras: [Front-Door]}
                     _correct_plan → (unchanged)
   4. dispatch       code: grab frame → YOLO → "🔴 Yes — person at Front-Door."

    4.1 The router is one structured call¶

    minder-router is a SwarmKit topology whose root agent has an output_schema and no tools. It sees the camera and device names of this house prepended to the message, and emits one JSON plan: kind (one of ten intents), and the fields that intent needs — camera, subject, device, operation, trigger, schedule. Ollama constrains decoding to the schema, so the shape is guaranteed; the prompt carries the meaning of each intent, because a grammar drops the field descriptions and a small model needs them (measured: skipping the pasted schema cut one intent from 55% to 29%).

    Why one call and not an agent with tools. Small models loop on list-tools, invent camera names and take different paths on identical input. Giving the router the names in the prompt and no tools removes every one of those failure modes. The plan it emits is a value; values are testable.

    4.2 The guards¶

    The plan passes through _correct_plan, a set of deterministic corrections, before anything acts on it. Each guard restates something an intent already means:

    • A scenario is a standing rule with a trigger — so "turn on the pump", with no trigger, is a command. This matters beyond accuracy: a scenario is stored, so a command misread as a rule silently never runs.
    • A device command must say what to do — so "what smart plugs do I have" is a listing, not an instruction to switch one. Answering a question by switching a device is the wrong kind of wrong for a house.
    • A message naming one of this house's cameras is about that camera — the names are Side-Gate, people type "side gate", and matching those is code's job.
    • A check across the cameras is a sweep, not a listing — "check all cameras and tell me what you see" once returned seven camera names.

    The guards are specific to the model deployed and are re-measured whenever it changes: on the original qwen2.5:3b they corrected 55 of 156 answers and were the difference between unusable and usable; on gemma3:4b they correct 16; on qwen3.5:4b they correct 3.

    4.3 Pre-routing: the certain cases never reach a model¶

    Before the router runs, router_learn.preroute decides the shapes code can be certain of: a greeting, an on/off order naming one device with no trigger or time word, a device or camera listing, a weather question. 45 of the 166 labelled cases; held to 100% precision by a test that runs every labelled case through it — a pattern that ever fires wrongly on a known message fails the build.

    Two deliberate refusals define the boundary. "turn off the pump at midnight" is not pre-routed: a time word makes it a scenario, and pre-routing it would switch the pump off now. "is the pump on" is not pre-routed: a question is never an order, however much it looks like one.

    Measured: guarded accuracy unchanged, raw accuracy up three points, the median route 10% faster, and a benchmark run a quarter shorter.

    4.4 The case set is the specification¶

    scripts/router_cases.json holds 166 single-intent utterances (plus ten compound ones, unscored) drawn from this house's own phrasings, each labelled with its intent. Every change to the router — prompt, model, guard — is measured against it, two ways:

    • scripts/bench_router_models.py calls Ollama directly with exactly the prompt the topology sends (it imports the same context builder), so candidates can be compared without restarting a live appliance. Flags reproduce every variable that ever mattered: #ctx context size, +gpu residency, +paste the compiler's schema-in-prompt, +preroute, +fewshot.
    • scripts/bench_router.py runs each case through the real topology on the running server — schema, guards and all. It is the number that means something absolutely; the direct harness with +paste reproduces it to the decimal and is used to pick.

    Both run under scripts/bench_isolated.sh, which stops every container but Ollama first and snapshots the router's context: a number taken while Frigate, Home Assistant and the VLM share the card is a number about that afternoon.

    The set grows from the phone. Replying wrong (or wrong: query) to a Minder answer stages the last routed message as a case with its expected intent; scripts/router_feedback.py --merge brings the labelled ones into the repository under review, tagged feedback. The place a misroute is noticed and the place the router's spec lives finally meet. scripts/harvest_router_cases.py does the same from the observation log in bulk.

    4.5 Which model routes, and why¶

    Measured through the real topology, in isolation, after the prompt fixes of the same change:

    model raw guarded guard corrections p50 resident with the VLM?
    gemma3:4b (default) 86.1% 94.0% 16 2.1 s yes — it is the VLM
    qwen3.5:4b 95.8% 96.4% 3 5.1 s no — evicts it
    qwen2.5:3b (previous) 60.3% 92.3% 55 2.1 s no

    gemma3:4b routes because it is already resident for vision. A 4 GB card holds one 4B model; a router on a different model evicts the VLM on every message and the next alert pays a cold load — that eviction was the bulk of a ~27 s round trip. One model, one runner, no reload. The 2.4 points qwen3.5 would add cost 2.4× the latency and the residency; .env.example says how to choose it.

    Three things were learned measuring this, each of which reversed an assumption:

    • The biggest lever was the prompt, not the model. A device_list line with examples, the conditional tense for scenarios ("if / when / let me know if / watch"), device status questions named as device_now, and "check the house" as a query moved every candidate by 2–9 points. The model swap alone, before those fixes, moved nothing.
    • Few-shot retrieval made it worse. The five nearest labelled cases as examples cost gemma3 six points raw: the phrasings closest to a message are its confusable ones, and the model copies the top example. Restricting to unanimous neighbours still did not beat the plain prompt. It is not in the live path; the harness keeps the flag for the next model.
    • Residency is not about context size. llama.cpp's auto-fit keeps ~1.7 GB of the card free for a multimodal model's worst-case projector, so a 4B VLM without num_gpu: 99 runs half on the CPU whatever num_ctx is (1783 of 3554 MiB in VRAM; p50 5.5 s against 3.7 s pinned). The router pins num_ctx 4096 / num_gpu 99 / keep_alive -1 to match the vision archetypes exactly — the same model with a different option is a second runner, and a request at Ollama's default keep_alive quietly un-pins the runner the vision path pinned.

    4.6 Dispatch is code¶

    The plan's kind selects a handler in minder_ops.py; none of them calls a language model to act:

    kind what runs
    query grab a frame per camera; YOLO for person/vehicle/animal (fast, deterministic); the VLM only for an open question on one named camera. An open question across all cameras is a YOLO sweep — one line per camera — never seven VLM calls
    snapshot / video grab and send
    device_now control_device: a status question reads state and never writes; an order calls exactly one Home Assistant service on exactly one entity, from a per-domain allowlist
    scenario author_scenario: the plan's trigger, device, schedule become a rule in /data/rules.json, shown back before it runs
    weather the Home Assistant weather entity, relayed verbatim — an agent added only hallucination here
    camera_list / device_list / setup / chat listings, onboarding, and the one path that is a conversation (minder-core)

    "Is the pump on?" is the case that shaped device_now. It routed correctly, and the handler's text parse saw "on" and switched the pump on. A question about a device is now a read, whatever operation the router filled in — test_device_status.py fails 14 of 19 on the old code.

    5. Perception: from a camera to an alert¶

    design/vision-architecture.md, design/frigate-mqtt-events.md, design/alert-quality.md §parts 1–2.

    camera ──RTSP──► Frigate (continuous detection, 5 fps on the substream)
                    │ MQTT frigate/events  (new / update / end)
                    ▼
            mqtt_listener ──► _match_and_fire_event ──► rule? cooldown?
            (minute poller = reconcile backstop; same state, never double-fires)
                    │
                    ├─ escalate rule  ──► VLM yes/no on a hi-res frame ──► alert or nothing
                    └─ plain rule     ──► SECOND OPINION ──► alert text now
                                                          └─► photo, description, clip as they exist
                    ▼
            alert bus (MQTT minder/alerts, durable per subscriber) ──► Telegram · Discord · dashboard

    5.1 Frigate detects; Minder decides¶

    Frigate is the perception sidecar: it decodes streams, runs a detector continuously and tracks objects. Minder never re-implements that. Minder configures it — frigate-init writes Frigate's whole configuration from the discovered camera list, the zones drawn on the dashboard and the platform profile's detector block — and consumes its events.

    Real-time over MQTT, with the poller kept. Alerts used to be up to a minute late because Minder polled /api/events on a cron. Frigate publishes every tracked object to frigate/events; Minder subscribes and reacts the instant one appears. The minute poller stays as the reconcile backstop for anything missed while MQTT was down, and both paths share one _match_and_fire_event and one dedup/cooldown state, so they can never double-fire.

    Rules match deterministically. A rule names cameras (or "all", "outside"), a condition whose words map to labels, optionally a zone, and actions. Escalate rules outrank plain ones for the same event so a broad "person" rule cannot shadow a per-camera "is it a weapon?" gate. Cooldown is per camera and condition (MINDER_ALERT_COOLDOWN, 600 s) and a rule may declare its own cadence.

    5.2 The second opinion¶

    Frigate ships with its default CPU detector — SSDLite MobileNet-v2 at 320×320 — running on a 352×288 substream. On the reference house it produced 111 person events on one camera in 36 hours. Forty of them on a contact sheet were two shapes: a fence post flickering at the right edge of the frame by day, and the dark bulk of a parked car under the porch light by night (one such event lasted 8828 s). Frigate scored both 0.71 — exactly what real people on that camera score — so no threshold separates them, and no area filter does either.

    Minder's own floor detector does. YOLOv8-n through the inference seam, on the very same snapshots, found 0 of 20 false positives to be a person — and missed some real ones at 352 px, which is why the gate looks at a bigger picture.

    So before a plain object rule alerts, _verify_event grabs a 640 px frame from the camera's main stream (the grab the escalate path already had) and asks the seam. Nothing there, then nothing on Frigate's own snapshot either — the moment Frigate saw it, because a fast person can leave between the two — and the alert is suppressed and recorded: the frames are kept, the health page counts it, scripts/audit_events.py suppressed lays the frames on a sheet. If the gate is ever wrong the evidence is there and the rule can say verify: off. If Minder cannot look — no frame, the seam failed — the alert goes out as before. Live cost: ~1.5 s for the grab and ~0.1 s for the look, ahead of a bot that polls every 10 s.

    The root cause is upstream and is not fixed here. The reference machine has a GPU Frigate does not use — the platform profile says cuda, the image target says cpu, and the health page reports the mismatch. Frigate on TensorRT would run a real YOLO on the detect stream and most of this would never fire. It competes with the VLM for the 4 GB card, so it is a measurement to make, not a default to flip; the second opinion is what makes the CPU detector liveable meanwhile.

    5.3 The alert, in order¶

    The text goes out instantly — the event has a rule, the second opinion agreed, that is enough. Then, in a thread that never blocks the alert path, as each exists: Frigate's boxed snapshot (the box is the point of the photo), the description, and the recorded clip. A live event has no snapshot at fire time and no clip until it ends; waiting for either inline would have dropped them.

    5.4 The description¶

    The line under the photo is the most-read thing Minder produces, and it was being written from the worst picture Minder has: the 352 px snapshot with a detection box burned into it. It is now written from the verified 640 px frame, and the prompt says where in it the subject is — "It is in the lower right of the frame" — from the seam's box, so a small model is told where to look rather than left to search.

    The prompt is grounded and conservative on purpose: anchored to what the detector found and which rule fired, forbidding the fabrication-prone moves (reading plates and signs, inventing entities, guessing counts, parroting the watch condition). scripts/vlm_bench.py showed the open prompt hallucinating on every model tried; this one removes it. Two sentences by default — what the subject looks like, then what it is doing — after scripts/bench_describe.py ran both styles over real frames on gemma3 and the second sentence added "carrying a green plant" and "looking towards the right" without inventing anything the one-sentence form had not.

    What both styles do invent is a person on a frame with no person, when told one was detected — the night-car frame came back as "a person in a dark jacket, moving right". That is the second opinion's job, and the reason the description never runs on a frame the seam rejected.

    The prompt lives in code, interleaved with the situation, rather than in the archetype's system message. That is measured, not neglect: moved to a system message the model started reading the timestamp overlay and the on-screen camera name. It honours a system message only when its output is grammar-constrained, which the yes/no confirm path is and free prose is not.

    5.5 Severity and escalation¶

    design/scenario-studio-severity-escalation.md

    A rule may carry severity (info / warning / critical) and an escalate block: a question the VLM must answer yes to on the frame — "is the person holding a weapon?" — before the alert and any actions fire. The deterministic match is only a pre-filter; the VLM is the gate. Critical rules use the cloud tier automatically, everything else local, cloud failing back to local. The verdict is a schema-constrained field, never the first word of prose — an off-shape reply is unverifiable, not a no — and a critical rule that cannot be verified still fires, flagged "unverified", because the one failure a security system may not have is a missed critical alert.

    6. The vision models¶

    design/two-layer-vision-models.md, design/vision-via-swarmkit.md

    Two layers, because they have different budgets:

    • Layer 1 — per-alert. Runs on every alert, so it must be cheap and local: the description above and the escalate yes/no, on gemma3:4b.
    • Layer 2 — interactive. "What is the person doing?", "is that dangerous?" — a model that reads and judges. Local by default; MINDER_QUERY_PROVIDER=openrouter puts a cloud model behind it.

    Object presence is YOLO's job, never the VLM's. The VLM describes a snapshot or answers an open question about one. That is the same split Frigate uses, and it is why a 4B model cannot fabricate an intruder into an alert.

    Every VLM call is a topology. The describe and confirm calls used to be hand-built HTTP requests to Ollama; they now run as vision-describe, vision-confirm and scene-query through SwarmKit. What that buys is not elegance: the model, its options and its provider are workspace configuration, and a call that fires on every alert finally leaves an audit record. Language models are reached only this way — there is deliberately no second abstraction over them in Minder.

    On the GPU, and that reversed the original design. The first note said CPU, reasoning that the GPU would thrash between detector and VLM — sound, and made without a measurement. A real question grabs a fresh frame, so its ~1,100 vision tokens can never hit the prompt cache; every call pays full prompt evaluation, and that is 131.8 s on the CPU against 18.0 s on the GPU. Every "CPU is fine" number before it had been taken against a stored snapshot, where the cache hides the entire cost. The rule that came out of it is in CLAUDE.md: measure with a frame the model has not seen.

    Three options must agree across every vision archetype and the router — num_ctx, num_gpu, keep_alive — and a test fails the build if they differ. Ollama reloads a model when the context size changes, and for a VLM that discards the cached image prompt: 0.2 s becomes 132 s.

    The frame is capped at 640 px (MINDER_VISION_MAX_WIDTH). The main stream's 2560×1440 is 4118 prompt tokens against a 4096 context, which Ollama answers with HTTP 400 — and the code read that error as "unsure". The capped frame is both faster and more accurate than the substream it replaced.

    7. Inference: what runs on what silicon¶

    design/inference-backends.md

    Everything above is what Minder decides. This is where the arithmetic happens — the part that changes when Minder runs on somebody else's hardware.

    7.1 Two roles, because hardware splits that way¶

    Role            Input    Output          Served by
ObjectDetector  frame    list of boxes   CPU · CUDA · OpenVINO · Coral · RKNN · Hailo
Embedder        crop     a vector        CPU · CUDA · OpenVINO · RKNN

    One interface with a run() is the tempting shape and the wrong one: a Coral Edge TPU runs a YOLO and cannot run a face embedder at all. A single interface lets a platform claim inference when it supports half of it, and the failure surfaces as an armed face plugin quietly finding nobody. Two roles means each capability is declared separately and a plugin needing an embedder on a detector-only box is refused at install, by name.

    7.2 Three rules¶

    1. Every role has a CPU implementation, always present. The degradation floor. A backend that cannot load falls back to CPU and records why (/data/inference_roles.json, read by the health page from any process). It never goes blind and never pretends to be the accelerator.
    2. The backend is chosen once, at the boundary, and injected. No module reads configuration at import time. That was a real bug — the detector pinned itself to the CPU as a side effect of being imported, before any configuration could be read.
    3. Backends return the same shapes, or they do not load. inference/_types.py is the contract.

    7.3 The floor is ONNX Runtime¶

    As PyTorch the floor was 1.66 GB to run one YOLOv8-n forward pass, on every platform including the ones with an NPU that never call it. As ONNX Runtime it is ~67 MB and cold start went from 13.0 s to 0.7 s. The cost: the model is exported at a fixed 640×640 because Coral and Hailo require fixed shapes, and across 9 frames × 3 class groups 23 of 27 results were bit-identical to PyTorch — the differences were a confidence at the second decimal and a duplicate box on a class no rule references. Accepted, measured, and re-checkable with scripts/probe_onnx_floor.py.

    7.4 Backends are drop-in, like plugins¶

    A backend is a directory under /data/backends/ (or backend-library/ in the repo) with a manifest — which roles it serves, what it costs, what device it needs — and a module loaded by path under a unique name, because two backends both named backend.py once collided in sys.modules. backend_install.py installs, lists and removes; the builtin cpu cannot be removed.

    A backend is done when the conformance suite says so. backend_verify.py is what an OEM is handed as the definition of done: parity against the floor on real frames (a box shifted three pixels passes; a lost person fails; a box on a different object fails), declared cost against measured cost, roles it claims against roles it answers, degradation (detection continues and the failure is reported), and output shapes. It is tested against backends deliberately broken in each of those ways, because a suite that cannot fail is decoration.

    Rockchip was verified without the board. rknn-toolkit2 ships a PC simulator; the RKNN backend converted, loaded and matched the floor numerically through the suite on a development machine. What a board still has to prove is timing and int8 quantisation — the reasons to have an NPU — and that is the only thing left to buy hardware for.

    7.5 What a box is, is data¶

    /data/platform.yaml says which backend serves each role, what detector Frigate should use, and what budget arming is measured against. Written at first boot by detection, overridable by shipping the file. The line that mattered most: Frigate's detector block used to be a hard-coded cpu literal on every machine, which was the entire camera-side cost of a port.

    Detection happens twice and the answers can disagree. Once on the host before any container exists (which image, which device passthrough, which host packages); once inside the container at first boot (which backend serves each role). Before the plan is applied they legitimately differ, and that difference is the most important thing the appliance can report: a machine with a GPU the container cannot reach looks exactly like a machine with no GPU — every internal check passes, consistently wrong, with a clean dashboard. So the host's answer is recorded (MINDER_HOST_PLATFORM) and compared, and when they differ the dashboard says so in words and names the file that fixes it.

    What happens without the host driver
    NVIDIA the stack does not start — loud, immediate
    Rockchip, Coral, Hailo, Intel everything starts and silently runs on the processor, forever

    The second row is what this whole section is against.

    8. The appliance: images, bootstrap, health¶

    design/appliance-bootstrap.md, design/health-monitor.md

    One Dockerfile, three targets, selected not generated. weights exports the ONNX floor at build time; base carries the CPU floor and no PyTorch; cpu (the default) adds PyTorch for the one feature that still needs it — training site-specific detectors. Accelerators are compose overrides (docker-compose.cuda.yml, .rknn, .coral, .hailo, .openvino), mutually exclusive because a machine has one, and a test caps the target count so this stays a handful of images and not a matrix.

    ./minder is the CLI, and it is POSIX shell so it works before Python and Docker are set up. bootstrap detects the hardware, asks the few questions that matter and writes .env — nothing else; host toolkits (the NVIDIA container toolkit, the Rockchip driver) are explained and offered, never silently installed, with what breaks if they are absent. up builds first and returns when the runtime answers, not when Docker reports the container started — both were rules people had to remember, and both were forgotten in ways that produced "verified" results reading stale code. status shows what is running, on what silicon, and what is degraded.

    The health monitor reports; it does not restart. Every 45 s it probes what the supervisor cannot see — a process that is up but not working: SwarmKit on 8321, Frigate, Home Assistant, Ollama, the adapters, the poll loop — with hysteresis (two consecutive failures before down), and writes /data/health.json for the dashboard. On a state transition it publishes an alert over the bus, so "Telegram blocked" reaches you on Discord. It never kills anything: a service busy mid-inference must not be mistaken for a hung one. Alongside liveness it carries the rows this document keeps returning to — the inference role and its fallback reason, the platform-vs-container mismatch, Frigate's detector, the alerts the second opinion suppressed.

    The doctor is a topology on a six-hour schedule: system health, a diagnosis, a backup. Backups are nightly to a host bind mount (backups/), restored from the dashboard.

    Operating it¶

    cd ~/minder
./minder bootstrap                # first time: detect the hardware, write .env
./minder up                       # build, start, wait until it can answer
./minder status                   # what's running, on what silicon, what's degraded
./minder logs minder              # watch
./minder down                     # stop

    ./minder up is the deployment command — not the raw compose start, which reports Running and ships nothing when the image has not changed. SwarmKit serves on 8321 (localhost only), the dashboard on 80; everything is network_mode: host, so nothing else on the machine may hold those ports. Telemetry is off by default (MINDER_OTEL=otlp exports to a collector on :4318); it once defaulted on and, with no collector, logged a connection error every 20 s until the real logs were unreadable.

    9. Scenario Studio: rules in words¶

    design/scenario-studio.md and its five phase notes.

    "Turn on the porch light when you see a car at the gate after 10pm" becomes:

    {"condition": "car", "cameras": ["Front-Gate"], "trigger_type": "vision",
 "actions": [{"type": "device", "device": "porch light", "action": "turn_on"}],
 "schedule": "22:00-06:00"}

    A rule is data — listed, inspected, deleted, shown back before it runs. The router produces the plan; author_scenario translates it; the rule engine in the Frigate server evaluates it with no language model at match time. The condition grammar grew by phase, each on the same machinery:

    condition source note
    object presence (person, car, animal) Frigate events the original
    count threshold ("more than two people"), debounced Frigate's retained count topics phase 1; "more than two" parsed from words
    presence or count in a zone zones drawn on the dashboard → Frigate zones phase 1.5
    zone crossing (entered / left) Frigate's zone transitions cross
    sensor state Home Assistant —
    time the clock at_time
    severity + VLM escalation the frame §5.5

    Site-specific detectors (phase 2, "quick mode"): capture frames from a camera, label them — optionally with a cloud model's help — train a small detector off the box, import the weights, and run it in a background loop on demand. Training does not belong on an appliance; the toolchain that would need is the argument in one paragraph.

    10. Detection plugins and face recognition¶

    design/detection-plugins.md, design/face-recognition.md, public doc face-recognition.md

    Optional perception — faces today, cartons on a belt tomorrow — added without a rebuild and without touching the detection path. A plugin is a directory in /data/plugins/ with a manifest, code, and a model fetched on install with a checksum; models are not baked into a ~3 GB image for a feature nobody may arm.

    Three levels of off, and they differ: not installed costs nothing; installed is authorable in rules and costs disk; armed has the model resident on a cadence and costs CPU. You can install something to look at it without paying for it, and MINDER_PLUGINS=off stops all of it.

    Declared cost makes arming safe. Every manifest states its cost as continuous load — 180 ms every 5 s is 3.6% of a core — and arming is refused with a reason you can act on when the budget is spent, instead of you discovering it as Frigate dropping frames.

    Plugins are classified by what they remember, not what they detect, and governance follows the kind: a detector keeps nothing between frames; an identifier keeps templates identifying a person and brings enrolment, consent, retention and provable deletion with it (a licence plate identifies a person as surely as a face — ANPR is an identifier); a tracker keeps cross-frame state and a memory bound.

    A plugin may not set severity and may not suppress an alert — its return value has no field for the first, and the runner has no route to the alert path for the second, asserted on its source. A wrong match costs a wrong name, never a missed event.

    Frames on demand. Frigate detects on the substream — enough to find a person, not to identify one. A plugin that needs resolution declares it and gets one main-stream grab per detection, cropped to the box Frigate found: 185×398 out of 2560×1440, 2% of the pixels, and the face detector runs in 9 ms instead of 453. The grab is deleted as soon as the plugins have looked.

    Face recognition is the first identifier and the one that shaped the governance. Enrolment is a human act on the dashboard; templates exist only for enrolled people; recognising a stranger is a first-class feature ("alert me if an unrecognised face is at the door after dark") and needs templates only for the people you know; there is no watchlist; a match annotates history and alerts and never unlocks, disarms or quietens anything; deletion is provable. Groups ("family", "guests this week") are the unit rules are written over, and guests expire.

    11. Memory: the house's history¶

    design/queryable-events.md

    Before this, the only log was a 500-entry ring buffer written by write_alert — a thing was recorded if and only if a human was notified. "Did anything happen at 3am that you didn't wake me for?" was unanswerable against a log defined as the things it told you.

    Notification is a property of an observation, not the condition for recording one. One table across every source — camera, device, sensor, rule, system, channel — because every question worth asking crosses them ("was the pump running when nobody was home?"). Every row carries notified, and when false, why not (cooldown, unarmed, suppressed). SwarmKit's audit log is mirrored in, so device actions and doctor findings are in the same history as detections; routing decisions are recorded too (router_log.py), which is what makes the benchmark growable from real traffic.

    A negative answer is only safe if Minder was looking. coverage.py records every camera's online/offline transitions, and an answer to "was anyone at the gate last night" carries the caveat when the gate camera was down for two of those hours. Built on SwarmKit's storage seam, so the local SQLite store becomes Postgres with a URL, not a rewrite — and the appliance's local store is never optional; anything central is a replica.

    The query path is the same shape as everything else: the router parses "what happened at the gate last night" into a structured Query; code executes it; the answer is rows with a caption.

    12. Channels¶

    design/messaging-adapters.md, design/discord-qr-invite.md, design/onboarding-webapp.md

    Adapters are thin. Telegram and Discord bots contain no logic; every message goes to POST /api/ops/message and every reply is a structured envelope (kind, text, media) the adapter renders its own way. Adding a channel is a subscriber and a renderer, never a change to the detection path. This exists because India blocked Telegram and the product needed a second channel without a rewrite.

    Alerts fan out over MQTT with a durable queue per subscriber. Minder publishes once to minder/alerts; each adapter is a persistent-session, QoS 1 consumer with a fixed client id, so an adapter that was down gets its backlog when it returns, and a blocked channel never blocks the others. The dashboard is a subscriber too.

    The dashboard (port 80) is onboarding — discover cameras, pair Home Assistant, choose a channel, pair a phone with a QR invite — and the operator's view: health, rules, zones, enrolled faces, history, backups. Session-cookie auth; the ops API is also reachable by the adapters and the doctor with an internal token that never leaves the box.

    13. State, tests, and the discipline around them¶

    State¶

    Where What
    minder_minder-data volume → /data cameras, rules, zones, channel config, monitor state, platform.yaml, inference_roles.json, health.json, alerts_suppressed.json, router_feedback.json, plugins, backends, media
    minder_ha-config volume Home Assistant's own configuration
    minder_frigate-media volume recordings (two days) and snapshots
    backups/ (bind mount) nightly backups, on the host
    workspace/.swarmkit/ audit log, run state, the observation store

    The compose project name is pinned to minder because volume names carry it; an unpinned project in a renamed directory silently creates new empty volumes while the real ones sit on disk — a wiped-appliance-shaped failure with a one-line cause.

    Tests¶

    ~700 tests run inside the image in CI (.github/workflows/ci.yml), because many reference /app paths; a handful that share module state run in their own process. Beside the unit tests is a second kind, each written after the failure it now prevents: guards that assert the system describes itself honestly. Every environment variable the code reads is passed by compose (test_env_plumbing — three variables were once documented and read by nothing); every root module is in the image (test_image_contents — one was missing and only a deploy found it); the model inventory matches the repository (test_models_doc); the vision archetypes and the router agree on residency options; no document instructs a deployment command that ships nothing; the Dockerfile has one entrypoint and a capped number of targets; pre-routing is 100% precise on every labelled case.

    Benchmarks are the other half of the tests¶

    scripts/ holds a benchmark for every decision that was measured: the router (bench_router*.py), VLM models (bench_vlm_models.py), the describe prompt (bench_describe*.py), the confirm schema, needle-in-frame ablations, the ONNX floor's parity, the seam's parity against the model it replaced. They are parameterised so the next change re-runs them instead of inheriting a conclusion, and bench_isolated.sh is the only way they run on the appliance.

    14. Decisions that were reversed¶

    Each looked obviously right until it was measured. A system that hides its reversals teaches the next person the wrong lesson, so they are collected here with the number that reversed them.

    Was Is What changed it
    VLM on the CPU — the GPU would thrash VLM on the GPU A real question grabs a fresh frame and never hits the prompt cache: 131.8 s against 18.0 s. Every prior number had reused a stored snapshot.
    The router on its own model (qwen2.5:3b, then qwen3.5:4b planned) The router is the VLM, gemma3:4b One 4B model fits the card; a second evicts the first on every message. Measured through the topology: 94.0% guarded at 2.1 s, resident.
    A bigger router model is the fix for misroutes The prompt and the taxonomy are The prompt fixes moved every candidate 2–9 points; the model swap alone moved nothing.
    Few-shot examples from the case set will help a small model They hurt it The nearest phrasings are the confusable ones; −6 points raw on gemma3.
    Residency is about num_ctx It is about num_gpu llama.cpp reserves ~1.7 GB for a multimodal projector; the model was half on the CPU at every context size until pinned.
    Alert on Frigate's word A second opinion first Frigate's CPU detector scores a fence post 0.71, the same as a person; the seam finds 0 of 20 false positives to be one.
    Describe the alert snapshot Describe a 640 px main-stream frame, told where to look The snapshot is 352 px with a box burned in; the two-sentence prompt on the better frame added detail and invented nothing.
    Keep camera frames low-resolution for the VLM Grab full-resolution, cap the longest edge at 640 Full resolution exceeded the context and returned an error read as "unsure"; the cap is faster and more accurate.
    The describe prompt belongs in the archetype's system message It stays in code, inline with the situation Moved, the model read timestamp overlays and invented entities; it honours a system message only under a grammar.
    PyTorch is the CPU inference floor ONNX Runtime is 1.66 GB against 67 MB, paid on every platform including those that never call it.
    A backend that falls back is fine if it works It must say so An accelerator silently not used is indistinguishable from not having one.
    A clean dashboard means a healthy box Only if something claimed an accelerator A GPU the container could not reach produced perfect health; the host's own detection is now compared.
    "Dark shadows" cause the porch false alerts A fence post at the frame edge and a parked car's bulk Forty snapshots on one sheet, in a minute; the numbers alone would not have shown it.

    Every one of these is a property of the specific model or machine, not a general truth.
