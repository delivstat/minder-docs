    Detector tuning: how the models were tested, and why resolution mattered more than the model¶

    This is the record of one deployment's detector work — what was measured, how, and what changed — written so the next installation can repeat the measurements rather than repeat the mistakes. Every number below came from the reference house: seven cameras, an 8-core CPU, no GPU that Frigate could use, and the appliance running in WSL2 (no /dev/dri).

    The one-line version: a better model on a 352×288 frame is still blind to a person 25 m away. The stream you detect on matters as much as the network you detect with, and a 300 px face is invisible to the face finder in the other direction. Measure your own cameras before you trust either default.

    The three measurements¶

    There are three ways to test a detector change, and each answers a different question. Do all three; each one caught something the others did not.

    1. Microbenchmark — "what does it cost?"¶

    Random input through the model in the same runtime Frigate uses, inside the Frigate container:

    import time

import numpy as np
import openvino as ov

core = ov.Core()
m = core.compile_model(core.read_model("/config/model_cache/yolov8n-320.onnx"), "CPU")
x = np.random.rand(1, 3, 320, 320).astype(np.float32)
for _ in range(3):
    m(x)  # warm up
t = time.time()
for _ in range(30):
    m(x)
print((time.time() - t) / 30 * 1000, "ms")  # 28 ms at 320, 46 ms at 416 on this box

    Frigate's own inference_speed in GET /api/stats is the same number measured live (17–22 ms once the graph was warm), and docker stats gives the container's total.

    What it tells you: whether the box can afford the change. Seven cameras at 5 fps is a worst case of 35 detections/s; at 28 ms that is one core, at 46 ms it is not. What it does not tell you: whether the detector sees anything.

    2. Offline recall — "does it see what the old one saw?"¶

    Frigate keeps a snapshot for every event, at the detect resolution. That is a free labelled set: whatever the previous detector called person over the last day, run through the new model offline, and count how many it agrees with. Contact-sheet the snapshots first (scripts/audit_events.py events) — some of what the old detector called a person is a fence post, and you are measuring the new model against the real ones.

    GET /api/events?after=<yesterday>&labels=person&limit=400   → snapshot per event
new model on each snapshot, at conf 0.3 / 0.5 / 0.7            → best person score

    This is the measurement that caught the regression. YOLOv8-n at 320 is a far better network than Frigate's default SSDLite — and on the substream it found 0 of 38 children cycling past the far gate that SSDLite had scored 0.69–0.76:

    camera (substream 352×288) real person snapshots YOLO-320 ≥ 0.7 ≥ 0.5 ≥ 0.3
    far gate (cyclists, ~20 px tall) 38 0 0–1 1–2
    front door (top-down, ~60 px) 82 11–19 16–29 29–47
    porch 10 (mostly one phantom) 0 0 0

    (The ranges are stretch vs letterbox resize; letterboxing helped the door a little and the gate not at all.) A 20 px person is below what a COCO-trained detector at 320 resolves, full stop. The old model scoring them 0.7 was not skill — it scored a parked car 0.71 too — but it was recall, and the new model had none. Had this gone straight to production the far gate would have gone quiet and looked "fixed".

    3. Live — "what does it do on the real stream?"¶

    Switch it on, and read three things for twenty minutes:

    • GET /api/stats: inference_speed, and per camera detection_fps against camera_fps.
    • GET /api/<camera>/latest.jpg?bbox=1&regions=1&motion=1: what is boxed, and where the motion regions are.
    • Events: what fired, against the same hour the day before.

    The live view is what showed the phantom was gone (two cars boxed as cars at 0.82–0.87, no person on either) — and, later, the side effect of the stream change below.

    Why resolution mattered more than the model¶

    Frigate does not run the detector on the whole frame. It finds motion, cuts a region around it (never smaller than the model's input, 320 px), and resizes the region to the model. On a 352×288 substream the region is the frame: a person 20 px tall stays 20 px. On the same camera's main stream scaled to 1280×720, the region is a 320 px crop at that resolution, and the same person is ~70 px inside it — a size any COCO detector handles.

    So the fix was not a third model; it was telling Frigate to detect on the main stream for the cameras that watch a far approach:

    { "name": "Front-Gate", "detect": { "stream": "main", "width": 1280, "height": 720 } }

    (the Detect on select on the dashboard camera card; MINDER_DETECT_STREAM=main for every camera). What it cost and what it gave, measured:

    substream 352×288 main stream → 1280×720
    decode (software, per camera) ~0.07 core ~0.3 core
    detection rate when nothing is happening ~5 fps, continuously — compression noise trips the motion gate 0.2 fps
    a person 25 m away, in the region the model sees 20 px ~70 px

    The second row was unexpected and pays for most of the first: at 352×288 the motion detector fires on noise all day, so every camera was running the detector at full rate all the time. At 1280×720 it fires when something moves. Per camera, because most cameras do not need it — the door camera has 60 px faces on the substream already — and each one on the main stream is a third of a core.

    The same lesson, the other way round: faces¶

    The face finder (YuNet) had the opposite problem. It finds a face at 250 px and finds nothing at 400 px or above — measured on the same face, scaled:

    image face found
    640 px 247 px yes
    1024 px 396 px no
    2000–4000 px 770–1550 px no

    A phone photograph has a 1200 px face, so every enrolment photograph came back "no face found", though the same model finds a 90 px face at the door every time. The fix (face_align.py, detect_any_size) detects on a copy no wider than 640 px and maps the landmarks back to the full-resolution photograph, so alignment still reads the real pixels. Camera frames pass through unchanged. Same rule as above: know the size envelope of the model, and put the pixels inside it — down for the phone, up for the gate.

    Checklist for a new deployment¶

    1. Microbenchmark the candidate in Frigate's container. Multiply by cameras × fps; if that is more than a core or two, stop here.
    2. Contact-sheet a day of events per camera. Note which cameras have far subjects (a person under ~40 px in the substream) and which have phantoms.
    3. Offline recall of the candidate over the real person snapshots. A camera where it drops to zero needs the main stream, not a different model.
    4. Switch on per camera: the model in /data/platform.yaml (frigate.detector + frigate.model), the stream per camera record. ./minder up or the dashboard applies it.
    5. Live for twenty minutes: /api/stats, the debug frame, events vs the same hour yesterday. Then a walk past each far camera, in daylight and at night.
    6. Keep the second opinion on. A better detector is still not a witness; the seam's look at the 640 px frame before an alert is what keeps a phantom from reaching your phone.

    The numbers above are one house's. Yours will differ in the direction that matters — which cameras are far, how noisy the substream is at night — and the three measurements take an hour.
